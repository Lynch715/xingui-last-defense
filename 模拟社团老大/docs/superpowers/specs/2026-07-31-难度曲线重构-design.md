## 1. 背景：60 个月的战役在第 0 个月就结束了

用户反馈"游戏性太差，五分钟就通关"。写了一个只招人、只强攻、能打就打的"莽夫机器人"跑 12 局验证：

```
=== brutal（最高难度）===
一统雾港: 12/12 局
平均月数: 0.6 / 上限 60
平均血拼场次: 7
平均点击次数: 40.3
```

单局逐仗追踪（死战难度，种子 20260731）：

```
月0 行动完毕: 人手72 现金26 士气75 合练8
  仗1 西关批发市场 兵力比2.21(优势) 出战58 人手72->61 地盘2
  仗2 金湾娱乐区  兵力比1.44(优势) 出战49 人手61->54 地盘3
  仗3 北站货场   兵力比1.34(优势) 出战43 人手54->60 地盘4
  仗4 东部新城   兵力比1.25(胶着) 出战48 人手60->65 地盘5
  仗5 南港码头   兵力比1.27(胶着) 出战52 人手65->58 地盘6
  仗6 红星船厂   兵力比0.97(胶着) 出战46 人手58->64 地盘7
  仗7 中央港区   兵力比1.10(胶着) 出战51 人手64->58 地盘8
结果: 地盘8/8 月份0 结局=unified
```

**最高难度下，全部 12 局都在第 0～2 个月结束。**

### 1.1 四条结构性根因（均经代码核实）

1. **血拼不消耗行动点。** `renderHall`（`app.js:448`）的说明文字明写"血拼本身不消耗行动点"，`launchBattle` 也确实不扣 `s.ap`。于是"60 个月 × 每月 3 行动点"这套节奏框架**从未生效**——一个月能打无限场。

2. **出战不锁人手。** `startBattle` 记录 `session.troops`，但从不从 `s.crew` 扣除；只有 `stageLoss` 产生的伤亡会减少 `s.crew`（`app.js:288`）。派 58 人出战只消耗 5～10 人，同一支队伍可以立刻再打一场。

3. **赢仗净赚资源。** `checkFactionDefeat`（`app.js:361`）在灭掉一家时 `s.crew+=12` 且 `addCash(s,20)`；`parley` 收编也加人手。滚雪球没有任何代价，追踪日志里人手多次不降反升。

4. **敌方成长慢一个数量级。** `enemyGrowth`（`app.js:369`）每月 `+2` 左右、上限 78；玩家 `recruit_crew` 每月两次共 `+30` 左右。`enemyAttack`（`app.js:370`）需要 `month>=6 && month%3===0 && 26% 概率`——第 0 月通关的话永远不会触发。

### 1.2 被浪费的既有内容

旧账剧情链、忠诚/怨气、`checkInsolvency` 资金链危机、招募市场、阿七成长、多结局评价——这些系统都已实现，但一局下来**一个都不会被触发**。内容是够的，缺的是节奏闸门。

## 2. 目标与非目标

**目标**

- 单局 40～60 分钟，打满 60 个月主战役
- 两条主要张力：**人手撑不住**（内部刹车）＋ **敌方主动扩张**（外部压力）
- 地图动态化：三家会互相吞并，每局地图走向不同
- 让既有系统（旧账、忠诚、资金链、收编、结局）在正常一局里被自然触发
- 留下常驻平衡测试，防止数值回归

**非目标**

- 不新增大系统（不做外交界面、不做全图分兵算术、不做多周目解锁）
- 不动三段式血拼的判定内核（`STAGE_SWING`、`stageOptions`、`applyStageChoice` 的段内逻辑）
- 不做"领先者被围攻"的动态结盟（会惩罚玩得好的玩家，本次明确排除）
- 不改 `estimateBattle` / `defenderPower` 的公式形状，只调其输入的数值

## 3. 兵力状态机

### 3.1 三个池子

`s.crew` 从单一数字拆成三个字段：

| 字段 | 含义 | 可出战 | 计入维护费 |
|---|---|---|---|
| `s.crew` | 能战 | ✅ | ✅ |
| `s.regroup` | 整补中（出战归来） | ❌ | ✅ |
| `s.wounded` | 养伤 | ❌ | ✅ |

派生函数 `totalCrew(s) = s.crew + s.regroup + s.wounded`。
`monthlyUpkeep` 的人手成本改用 `totalCrew(s)`——**养伤的人也要吃饭**，这是"打不起"的一部分。

### 3.2 出战与结算

- **出战即扣人**：`startBattle` 立即执行 `s.crew -= troops`。
- **段内伤亡**：`applyStageChoice` 的 `stageLoss` 不再动 `s.crew`（人已经不在池子里），只累加 `session.losses`。
- **战后结算**（`finishBattle`，胜/败/撤退三种结局同样处理）：
  - 幸存者 `troops - session.losses` → `s.regroup`
  - 伤亡 `session.losses` 中 `round(losses * 0.55)` → `s.wounded`，其余阵亡永久消失
  - `s.casualties` 仍累计全部伤亡（供剧情条件使用）

`parley` 收编来的人直接进 `s.crew`（他们没参加过我方的仗），保持现有手感。

### 3.3 每月回流

在 `advanceMonth` 中、`applyEconomy` **之前**执行 `recoverCrew(s)`：

- **整补**：`back = max(5, ceil(s.regroup * 0.5))`，`s.regroup -= back`，`s.crew += back`
  → 约 **2 个月**归队完毕
- **养伤**：`heal = max(1, ceil(s.wounded * 0.22))`
  → 约 **4～5 个月**才能全部回归
- **医药费**：`cost = round(s.wounded * 0.4 * 10) / 10` 万/月
  - 现金足够：正常扣费并按上式回归
  - 现金不足：`heal` 减半（向下取整，至少 0），`change(s,"morale",-4)`，写一条 `bad` 日志

数值意义：派 60 人打一仗，伤亡约 12 人 → 48 人整补、7 人养伤、5 人阵亡。下月回 24，再下月回 24——**两个月才恢复战力**，同时留下一批要养近半年的伤员。

### 3.4 人手上限

新增 `crewCap(s) = 40 + 已占地盘数 * 20 + (各地盘 level 之和 - 地盘数) * 6`

- 1 块地：60 人
- 4 块地（含一处 Lv.2）：126 人
- 7 块地（含三处 Lv.2）：198 人

`recruit_crew` 的实际收益裁剪为 `min(gain, crewCap(s) - totalCrew(s))`；到顶时该行动置灰，`lockedText` 显示"老街养不下更多人了"。

**这是本设计里"扩张有代价"和"扩张有回报"的同一个旋钮**：想养更多人必须先拿地，拿地又需要人。用户明确要求"偏紧一点"，故取 `40 + 20×地盘` 而非初稿的 `45 + 22×地盘`。

### 4.1 初始驻防上调约 50%

`TERRITORY_DEFS` 的 `guard` 字段：

| 地盘 | 现在 | 改为 |
|---|---|---|
| 旧城老街（玩家） | 24 | 24（不变） |
| 南港码头 | 46 | 68 |
| 红星船厂 | 53 | 78 |
| 金湾娱乐区 | 43 | 64 |
| 东部新城 | 56 | 82 |
| 西关批发市场 | 40 | 60 |
| 北站货场 | 48 | 70 |
| 中央港区 | 82 | 120 |

校准后开局（42 人 + 三名旧部，未行动）打西关批发市场，攻守比约 **0.89（胶着）**；改动前是 2.21。想稳赢需要先攒两三个月。

### 4.2 成长与上限

`enemyGrowth` 改为：

```
add  = (1 + income/18) * (1 + 该家地盘数 * 0.25) * diff(s).enemyGrowth
上限 = 55 + 该家地盘数 * 18   （中央港区固定 140）
```

做大的势力防线会明显变厚：独占 4 块地的一家上限 127，而不是现在人人 78。

## 5. 敌方主动扩张

### 5.1 触发

`s.factions[x]` 新增 `ambition` 字段（初值 0）。每月 `enemyTurn(s)` 中：

```
ambition += (1 + 该家地盘数 * 0.5) * diff(s).enemyGrowth
```

`ambition >= 12` 时发动一次进攻并归零。单块地的一家约 **8 个月**动一次，三块地的约 **5 个月**一次——60 个月里合计 12～18 次 AI 行动。

每月最多允许**一家**行动：取 `ambition >= 12` 者中数值最高的一家出手，**只有出手的这家归零**，其余保留累积值等待下月。这避免同月连环易主把玩家打懵，同时保证被压住的一家迟早会动。

### 5.2 目标与判定

- **目标**：该家地盘的相邻地盘中，不属于自己的、`guard` 最低者。**包括玩家的地盘**。
- **攻方战力**：`该家地盘数 * 16 + 该家未受伤头目 leaderScore 之和 + s.month * 0.5`，再 × `diff(s).battle` × `(0.85 + rng()*0.3)`
- **守方战力**：`guard * 1.18 * 1.15 + 守方头目 leaderScore 之和`
  - `1.15` 是守方加成，防止 AI 滚雪球过快
  - 玩家为守方时，守方头目取未受伤的前两名（沿用 `enemyAttack` 的现有逻辑）
  - 目标处于**驻防期**（见第 6 节）时，`guard` 只按 70% 计入
- **结果**：攻方胜则易主，新主 `guard = round(原 guard * 0.55) + 12`，`stability = 50`

### 5.3 玩家可见性

- **AI 打 AI**：写入月度日志，并在地图页地盘卡上标出新归属。不弹窗（60 个月里十几次弹窗太吵）。
- **某家被灭**：弹窗（复用 `checkFactionDefeat` 的叙事，但不给玩家 `+12 人手 +20 万`——那是玩家自己打赢才有的奖励）。
- **AI 打玩家**：沿用现有 `enemyAttack` 的弹窗战报。

### 5.4 与现有 `enemyAttack` 的关系

`enemyAttack` 保留，作为"针对玩家的骚扰性反扑"，但触发条件放宽：去掉 `month % 3 !== 0` 限制，改为 `month >= 4` 且概率判定。`enemyTurn` 负责的是**战略级扩张**（会真的丢地），`enemyAttack` 负责**战术级消耗**（掉人手、掉士气）。两者职责不重叠。

## 6. 新地盘的驻防期

`s.territories[id]` 新增 `settling` 字段（数字，剩余月数）。

- 玩家打下一块地：`settling = 3`
- 每月 `advanceMonth` 递减 1
- `settling > 0` 期间：
  - 该地盘收入减半（`monthlyGross` 中 `* 0.5`）
  - 被进攻时 `guard` 只按 70% 计入（见 5.2）
  - 25% 概率触发"街面不服"：`现金 -4`、`s.crew -3`、`support -3`，写一条 `warn` 日志
- **免除方式**：新增行动「坐镇新地盘」（1 AP），指定一名未受伤头目驻守，`settling` 立即归零，该头目当月不能参战

这是"驻防分兵"的最小实现——扩张有代价，但不需要玩家全程做减法。

## 7. 行动点与新行动

### 7.1 血拼消耗 1 行动点

`launchBattle` 增加 `s.ap >= 1` 前置检查并扣除。`renderHall` 与 `renderBattle` 的说明文字同步修正（当前写的是"血拼本身不消耗行动点"，改为"发起进攻消耗 1 行动点"）。

### 7.2 新增三个行动

| 行动 | 消耗 | 效果 | 每月上限 |
|---|---|---|---|
| 安顿伤员 | 1 AP + `wounded * 0.6` 万 | 当月伤员回归量翻倍，士气 +3 | 1 |
| 加固驻防 | 1 AP | 12 名能战人手 → 指定己方地盘 `guard +15` | 1 |
| 坐镇新地盘 | 1 AP | 指定头目清除一块地的 `settling` | 1 |

「安顿伤员」在 `s.wounded === 0` 或现金不足时置灰。
「坐镇新地盘」在无 `settling > 0` 的地盘时置灰。

「加固驻防」把人手转成驻防，是**不可逆**的：转过去的 12 人从 `s.crew` 扣除且不进入任何池子，因此不再计入 `totalCrew`、不再产生人手维护费——他们的开销由既有的地盘维护费（`monthlyUpkeep` 中的 `territoryCost`）承担。这让"防守"成为一个真实的资源取舍，而不是免费的。

## 8. 界面改动

1. **顶部状态条**：人手一栏由单一数字改为 `能战 / 整补 / 养伤` 三段（`index.html` + `style.css`）。
2. **出战界面**：人手滑杆 `max` 改为 `s.crew`（能战），并显示"整补中 N 人、养伤 N 人"作为灰色注解。开战门槛由 `S.crew < 10` 改为能战人手 < 10。
3. **地图页**：`settling > 0` 的地盘卡显示"未稳（剩 N 月）"角标；非玩家地盘显示当前归属（AI 易主后要能看出来）。
4. **议事堂**：`crewCap` 到顶时招人按钮置灰并说明原因。

## 9. 存档迁移

`normalizeState` 需要处理旧存档（`VERSION` 保持 1，避免让现有玩家存档直接作废）：

- `s.regroup` / `s.wounded` 缺失时补 `0`
- `s.factions[x].ambition` 缺失时补 `0`
- `s.territories[id].settling` 缺失时补 `0`
- 旧存档的 `s.crew` 原样保留（全部视为能战）

数值字段一律走 `Number.isFinite` 校验并夹到合法区间，与现有 `insolvencyMonths` 的处理方式一致。

## 10. 平衡测试（常驻）

本次诊断用的 `tests/rush.sim.mjs` 转正为 `tests/balance.test.mjs`，纳入 `README` 的检查流程。断言：

| 断言 | 阈值 |
|---|---|
| 莽夫策略（标准）通关月份中位数 | ≥ 30 |
| 莽夫策略（标准）通关率 | < 60% |
| 莽夫策略（死战）通关率 | < 25% |
| 完全不行动的玩家，60 个月后剩余地盘 | ≤ 2 块 |

**最后一条断言同样重要**：既要防止"5 分钟通关"，也要防止矫枉过正变成"怎么打都打不完"。

## 12. 已知风险

1. **空月份风险**：60 个月里若出现连续"没兵可打、只能点下一月"的月份，节奏会变得枯燥。缓解：三个新行动 + 每 2 个月一次随机事件 + AI 行动日志，让等待期仍有信息流入。校准阶段需要人工试玩确认，不能只看测试通过。
2. **AI 吃太快**：若 `enemyTurn` 胜率偏高，玩家可能在中期面对无法翻盘的巨无霸。守方 1.15 加成与"每月最多一家行动"是两道保险，仍需靠第 10 节第 4 条断言监控。
3. **维护费叠加过狠**：`totalCrew` 计入维护费后，大量伤员 + 医药费可能与 `checkInsolvency` 叠加成死亡螺旋。校准时需单独观察破产结局的出现率，若超过 15% 则下调医药费系数。
