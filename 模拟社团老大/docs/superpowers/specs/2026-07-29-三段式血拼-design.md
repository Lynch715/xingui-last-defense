日期：2026-07-29

影响文件：`app.js`、`style.css`、`tests/structure.test.mjs`

## 1. 背景：现在的血拼哪里不对

以下六条均经代码核实，不是手感判断。

1. **整场只有一次骰子。** `resolveBattle` 用 `roll = .84 + rng()*.34`，`won = ratio*roll >= 1`。ratio < 0.848 必败、> 1.191 必胜，中间才随机。
2. **三段战报是装饰。** `buildBattleNarrative` 的开局／僵持／决胜三段文字，分别由 `tactic`、`estimate.ratio>=1`、`won` 三个**已知量**拼出，不是打出来的。README 宣传的"三段战报"在机制层不存在。
3. **14 个角色中 6 个的战斗特性是空文字。** 战斗代码只认 5 个 id（`zhaokui`/`chengye`/`weixiaolou`/`hewanshan`/`aqi`）。未实现：沈川「亲自出战时士气不会低于45」、韩彪「强攻时可压住对方一名猛将」、谢九「连胜时战力上升」、唐霁、方景曜、顾长风。
4. **五维有两维半是废的。** `leaderScore` 只用 `force`/`command`；`scheme` 仅奇袭、`charm` 仅劝降、`business` **完全不参与战斗**。加上 `renderBattle` 自动选好前三，"选头目"实际是废操作。
5. **战术之间没有克制。** 四种战术只是 ±10% 威力带宽 + 伤亡系数，防守方没有战术。「攻心劝降」不劝降任何人，只是"弱 8%、死得少 28%"，与游戏的收编／义威利主题脱节。
6. **地盘没有战斗个性。** 打红星船厂和打金湾娱乐区，除 `guard` 数值外完全一致。

## 2. 目标与非目标

**目标**

- 三段成为三次真实判定，每段停下来让玩家决策
- 决策选项由**在场头目**提议 —— 使选将成为核心决策
- 兑现全部 6 个空特性，让 `scheme`/`charm`/`business` 真正参战
- 引入中途撤退，使"投多少人、何时止损"成为策略
- **不改动现有难度平衡**

**非目标**

- 不做敌方决策 AI（防守方的应对烘焙进判定与守方特性即可）
- 不做地形系统（第 6 条留待后续）
- 不动 `estimateBattle` / `defenderPower` 的既有公式

## 3. 架构决策

### 3.1 可续存的战斗会话

三段式会产生跨越多次交互的中途状态。若战斗只存在内存中，则"投入 100 人 → 开局打崩 → 刷新 → 此战未发生"成为免费读档大法。

**决策：把战斗状态存进存档，做成可恢复的状态机。**

```
startBattle(s, plan, rng)              -> session
stageOptions(s, session)               -> Option[]      （纯函数）
applyStageChoice(s, session, id, rng)  -> {narrative, ended, outcome}
finishBattle(s, session, rng)          -> report
```

### 3.2 不走 modalQueue

战斗**不得**复用 `modalQueue`／`pumpModal`。该队列用于"打断"，且刚修复过两个时序缺陷（结局被排队弹窗覆盖、`debtCrisisQueued` 落盘卡死）。战斗是线性流程，另起炉灶更安全。

**界面：在 `#panel` 内实现战斗视图。** 顶部一条 −100…+100 的势条，中部为逐段累加的战报卷轴（已结束的段落保留在上方），底部是当前段的头目提议。

### 3.3 选项必须是推导结果

`stageOptions` 是纯函数，同一 session 调用两次结果必须完全一致。存函数进 localStorage 不可行；存选项快照会与状态漂移。刷新后按存档重建界面，玩家看到同一组选项。

## 4. 势的数学

保留 `estimateBattle` 不动，`ratio = power/def` 仍为基准。

```
U_i ~ U(0.705, 1.295)                                     // 每段 ±29.5% 临场波动
Δ_i = (ratio × U_i × choiceMult × mods.multRest − 1) × 33.3
势  += Δ_i                                                 // 三段累加
胜 ⟺ 三段结束时 势 ≥ 0
```

`mods.multRest` 是单挑等事件留下的持续修正（初值 1），作用于**其后所有段**。`choiceMult` 只作用于当段。

### 4.1 为什么是 ±29.5%

旧版单骰 `U(0.84,1.18)` 标准差为 0.098。三段取平均会把方差压掉 √3，故每段须放宽至 0.295，**三段平均后的总波动才与旧版一致**。这是保持平衡不变的关键常数，不可随意调整。

### 4.2 平衡校验

| ratio | 旧版胜率 | 新版胜率 |
|---|---|---|
| 0.85 | 0%（必败） | 3% |
| 0.90 | 20% | 13% |
| 1.00 | 53% | 50% |
| 1.10 | 80% | 82% |
| 1.19 | 100%（必胜） | 95% |

中段几乎重合，现有数值无须重调。两端更优：旧版的必败／必胜死区被消除，保留小概率翻盘与阴沟翻船。

### 4.3 选择的影响带宽

`choiceMult` 限制在 **0.90–1.25**。足以让选择有分量，又不至于盖过战前部署。

### 4.4 逐段伤亡

```
段伤亡 = troops × baseRate × choiceCasualtyMult × (0.8 + rng()×0.45) ÷ 3
```

打满三段付三段的血；第二段鸣金只付两段。这是撤退机制的地基。

### 4.5 三态结局

`outcome` 由布尔改为 `win` / `loss` / `retreat`。

撤退代价：

- 保住未损失人手，不夺地
- 士气 −6、声望 −2（完败为 −10 / −3）
- 若赵魁在阵，且玩家本场**选过"压上去"之后仍撤退** → 赵魁怨气 +8（听了他的话又临阵收手）
- **叶蓉在场 → 撤退不掉士气**（`business` 首次具备战场价值）

## 5. 头目提议

### 5.1 组装顺序

每段最多 **5 个**选项：

1. **压上／稳住** —— 恒定保留
2. **在场头目专属提议** —— 按 `priority` 降序取前 2
3. **鸣金收兵**（第 2 段起）—— 恒定保留

> **实现修正（原稿为「最多 4 个」）。** 上限 4 会在第 2 段起把「稳住」挤掉（鸣金 + 2 专属 + 压上 = 4），
> 而 `resolveBattle` 自动战斗包装器依赖 `hold` 恒在，无头测试会直接崩。改为上限 5 并把三个通用项
> 设为不可挤占。`priority` 值：backdoor 5 ＞ duel 4 ＞ parley 3 ＞ flank/supply 2 ＞ rearguard 1；
> 若不排序，`[苏曼青,魏小楼,赵魁]` 这种阵容会静默丢掉 `duel`，使整个单挑机制对该阵容不可达。

### 5.2 提议表

效果按属性缩放，非固定值。

| 提议 | 提议者 | 出现条件 | 效果 |
|---|---|---|---|
| 压上去 | 通用／赵魁代言 | 常驻 | 势 ×1.15，伤亡 ×1.30；赵魁在场 ×`(1.15+武/1200)` |
| 稳住阵型 | 通用 | 常驻 | 势 ×1.00，伤亡 ×0.85 |
| 鸣金收兵 | 通用／苏曼青代言 | 段 ≥ 2 | 立即撤退 |
| 「左翼是空的」 | 苏曼青 | 段 ≤ 2 且 谋略 ≥ 70 | 势 ×`(1+谋/900)`，伤亡 ×0.90 |
| 「后门我留着呢」 | 魏小楼 | 该地未查明情报 | 势 ×1.12，当场写入 `s.intel[targetId]` |
| 「让我去喊一嗓子」 | 程野 | **势 > +20** | 势 ×0.88；胜利时转化敌兵 `round(enemyLoss×魅/260)` 进人手，且该地稳定度 −10 |
| 「那个人交给我」 | 赵魁／韩彪／谢九 | 敌方有未受伤猛将 | 单挑，见 5.4 |
| 「退路我安排好了」 | 叶蓉 | 段 ≤ 2 | 伤亡 ×0.75，撤退不掉士气 |
| 「我来断后」 | 阿七 | 段 ≥ 2 | 伤亡 ×0.85，阿七 exp+3、受伤率↑ |

### 5.3 被动（不占选项位，写入 `session.mods`）

- **沈川在阵** → 全场士气下限 45 ← 兑现空特性
- **谢九在阵** → 连胜 ≥ 2 时全程势 ×1.05；本场败北则忠诚 −8（而非 −2）← 兑现空特性
- **唐霁收编后在阵** → 胜利时全员功劳 ×1.5 ← 兑现空特性

### 5.4 单挑

```
对手 = 敌方未受伤头目中武力最高且 force>=60 者
      （原稿表格写「敌方有猛将」，但全局只有韩彪的 type 是猛将，单挑几乎不会出现；
        改用 force>=60 的门槛后 east 2 名、wan 1 名、long 1 名守将合格）
      中央港区属「港城同盟」，同盟名下没有任何头目 —— 此时回退到已被打散的
      三家龙头（side==="defeated"）出来压最后一阵，否则最该有单挑的终局之战反而没有
p = 0.5 + (我.force − 敌.force)/200
韩彪在阵 → p += 0.15        ← 兑现「强攻时可压住对方一名猛将」
                              （韩彪本人出战时同时享受高武力与该加成，为有意设计）
p = clamp(p, 0.15, 0.85)      ← 加成后再夹取，保证上限不被突破
胜：敌将 injured = rand(1,3)；`mods.multRest ×= 1.25`；我将 merit += 8
败：我将 injured = rand(1,3)；`mods.multRest ×= 0.85`；士气 −5
```

**一场血拼只能单挑一次**（`mods.dueled`）。东潮会有两名合格守将，不设此限时 `multRest`
可叠到 1.5625，配合谢九连胜加成达 1.64，第三段直接变成走过场。

**`multRest` 只作用于后续段。** 单挑必须在当段 `delta` 算完之后才结算，否则字面意义的
「剩余段修正」会抬高它自己发生的那一段，使第三段单挑变成直接左右胜负的抛硬币。

**敌将伤病必须随月份愈合。** `advanceMonth` 原本只给己方疗伤，而 `factionLeaders` 过滤
`injured<=0` —— 敌将永久带伤会让 `checkFactionDefeat` 的战后收编路径彻底失效，赢一次单挑
就永久断掉招募韩彪/魏小楼的可能，属于自毁式设计。

### 5.5 劝降门槛与代价

「势 > +20」把劝降从"弱 8% 的攻击选项"改为"须先打出优势才能摘的果子"。程野的价值随之从被动加成变为"打赢了才用得上"，与游戏收编主题一致。

**但只加门槛不够。** 首版（势 ×0.95、转化率 魅/200）实测下来是解锁即必选：对比同局势选「稳住」，
净人手 **+9 ～ +22**，而势的代价只有约 **1.8**，且拿下的地盘稳定度完全相同。已调整为势 ×0.88、
转化率 魅/260、并让劝降拿下的地盘稳定度 **−10**（收编来的终究是对家旧部，街面上一时压不住）。
调整后势的代价约 **12.6**，与单段 ±11 的波动同量级 —— 胶着局里选劝降真的可能把胜势打没，
劝降从"白拿"变成了"用赢面换人头"。

### 5.6 血拼进行中的封锁

`advanceMonth` 与 `applyAction` 都必须拒绝执行。前者会疗伤、触发叛逃与敌方反扑，
在半场战斗中途改变可选项；后者会照常扣行动点。二者是同一个漏洞的两半。

## 6. 存档与续战

### 6.1 会话字段

```js
s.battleSession = {
  targetId, leaderIds, troops, tactic,
  stage,                 // 1..3，当前等待决策的段
  momentum,
  ratio,                 // 开战时冻结
  losses, enemyLoss,
  mods: { multRest, casualtyRest, moraleFloor, convertRate },
  log: [{ name, text }]  // 已完成段落，用于战报卷轴
} | null
```

### 6.2 两条硬性规则

**① `ratio` 开战时冻结。** 否则单挑失利导致己方头目受伤后，`estimateBattle` 会重算出更差的 ratio，玩家会看到势莫名塌方。所有中途变化一律走 `mods`，显式可控。

**② 伤亡逐段扣除并存档。** 每段结算后立即 `s.crew -= 段伤亡` 并 `saveGame()`。存档在任何时刻自洽：中途崩溃既不会凭空多人也不会少人，最坏情况仅丢失一块未打下的地。此规则同时堵死"打崩即刷新"。

### 6.3 版本兼容

**不改 `VERSION`。** 现行 `normalizeState` 对 `version !== VERSION` 直接判 null，升版会使所有旧存档失效。`battleSession` 为纯新增字段，缺失即 `null`，照 `insolvencyMonths` 的既有做法在 `normalizeState` 中补默认值，旧存档无缝迁移。

`normalizeState` 另须**校验并丢弃损坏的 session**（stage 越界、`targetId` 不在 `TERRITORY_DEFS`、`leaderIds` 全部无效）：置 null 并记一条"战斗中断"日志。人手已按段扣除，丢弃是安全的。

### 6.4 界面分支

`renderBattle` 开头判断：`s.battleSession` 存在 → 渲染战斗视图；否则渲染部署表单。玩家因此不可能同时开启两场战斗。

### 6.5 战果仍走一次 modal（与结局时序的耦合）

三次**段内决策**在面板里完成，但**最终战果**必须仍经 `enqueue(...)` 弹一次 modal，与现状一致。

原因是本仓库刚修复的结局时序（P1）：`endGame` 会清空旧队列、挂起 `pendingEnding`，再由 `pumpModal` 在队列排空后调用 `flushEnding()` 揭晓结局。若终局之战的战果只画在面板里、不入队，则 `finishBattle` → `checkVictory` → `endGame` 时队列为空，结局会**立刻覆盖玩家还没看的最后一战战果**——正是 P1 修好的那个 bug 的翻版。

保留这一次入队，即可自动获得正确顺序：**三段决策（面板）→ 战果 modal → 结局**。

**实现约束：`finishBattle` 不得自行调用 `showEnding`**，一律沿用 `endGame` 的挂起机制。

## 7. `resolveBattle` 保留为包装器

```
resolveBattle(s, plan, rng) === startBattle + 三段全选 hold + finishBattle
```

三点收益：现有测试无须改动；提供无头"自动战斗"路径；**同时充当平衡回归夹具**——第 4.2 节的胜率表可直接跑出验证。

## 8. 测试

新增至 `tests/structure.test.mjs`：

1. 同 ratio 下 `resolveBattle` 胜率与旧版一致（固定 rng 序列，锁死平衡）
2. 势累加正确，胜负判定严格在 `M ≥ 0`
3. 第 2 段鸣金 → 伤亡**严格小于**同 rng 序列下打满三段的伤亡、不夺地、`outcome==="retreat"`、士气 −6
   （逐段 rng 使"恰好 2/3"不可断言，故断言方向而非比值）
4. `stageOptions` 幂等：同 session 连调两次 `deepEqual`（保证刷新可重建）
5. session 经 `JSON.parse(JSON.stringify())` 后仍能继续推进
6. 单挑：韩彪在阵时 p 提高 0.15
7. 劝降在 `势 ≤ 20` 时不出现、`势 > 20` 时出现
8. `normalizeState` 丢弃 stage 越界的 session
9. 终局之战胜利后：战果先入队，`pendingEnding` 挂起，队列排空后结局才显示（守住 6.5 的时序）

## 10. 已知取舍

- **单段波动大。** ±29.5% 意味着一段之内可能从优势掉到劣势。这是三幕剧所需的反转，但若日后希望局势更可预测，须调小该值并接受三段合计比旧版更确定——两者不可兼得。
- **每场固定 3 次点击。** 已确认接受（一局 15–30 场，合计 45–90 次）。若后续觉得碾压弱敌太烦，可加"战报详略"开关，但本次不做。
- **地盘战斗个性（诊断第 6 条）本次不解决。**
